2. ARCHIVO: modules/auth/auth_service.py (MODIFICADO)
   --------------------------------------------------------------------------------
   Cambios en SQL y lógica de autenticación:

   a) Consulta de login (línea 64-77):
      ANTES: SELECT ... FROM usuario WHERE ... (sin JOIN)
      DESPUÉS: SELECT u.id, u.nombre, u.correo, u.contrasena AS password_hash,
               u.estado, COALESCE(u.intentos_fallidos, 0) AS intentos_fallidos,
               u.bloqueado_hasta, u.rol_id, r.nombre AS rol_nombre
               FROM usuario u LEFT JOIN rol r ON u.rol_id = r.id_rol
      - Se agregó LEFT JOIN con la tabla rol para obtener el nombre del rol.
      - Se cambió el campo "rol" por "rol_id" (nombre real en la BD).

   b) Validación de estado (línea 94-95):
      ANTES: estado = user["estado"] or "Activo" / if estado == "Inactivo"
      DESPUÉS: estado = user["estado"] / if estado is False
      - El campo estado ahora es BOOLEAN (TRUE=Activo, FALSE=Inactivo).

   c) Validación de bloqueo (línea 111-137):
      ANTES: if estado == "Bloqueado": ... UPDATE SET estado = 'Activo'
      DESPUÉS: Se verifica bloqueado_hasta directamente. Si ya pasó el tiempo
               y estado es FALSE, se reactiva con UPDATE SET estado = TRUE.
      - Se eliminó la lógica de estado "Bloqueado" como string.
      - Ahora se usa bloqueado_hasta para determinar si está bloqueado.

   d) Bloqueo por intentos fallidos (línea 148-158):
      ANTES: UPDATE SET estado = 'Bloqueado'
      DESPUÉS: UPDATE SET estado = FALSE
      - El estado de bloqueado ahora se marca como FALSE (booleano).

   e) Login exitoso (línea 197-204):
      ANTES: UPDATE SET estado = 'Activo'
      DESPUÉS: UPDATE SET estado = TRUE
      - Se usa booleano TRUE en lugar del string 'Activo'.

   f) Generación de JWT (línea 215-221):
      ANTES: "role_id": user.get("rol")
      DESPUÉS: "role_id": user.get("rol_id"), "role_name": user.get("rol_nombre")
      - Se agregó el nombre del rol al token JWT para autorización.
